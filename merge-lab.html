Merge Lab

A merge puzzle where I built the tuning tools before I needed them: a level editor and a win-rate dashboard sitting right next to the game.

Role
Solo, design and build
Timeline
3 weeks
Platform
Mobile web
Focus
Balancing workflow and instrumentation
Play Merge Lab

Win rate, level by level

Problem

Tuning a puzzle game solo usually goes: change a number, rebuild, play it yourself, decide it feels about right, move on. That's not tuning, that's guessing with extra steps, and you only find out you were wrong when someone else plays it. I wanted to know whether building the tools first would change how the game turned out.

Writing a merge loop is straightforward. Writing it while also building an editor that changes the game live and a dashboard that says something useful is three things that all have to agree with each other. The editor had to apply changes without a rebuild or I'd never use it, and the dashboard had to point at the problem level rather than hand me a wall of numbers I'd ignore by the second session.

The game and the tools beside it

Decisions

Tools first, even though it felt backwards

I built the editor and the dashboard alongside the game instead of shipping the game and bolting tooling on later. What it costs: it took noticeably longer before I had anything that looked like a finished game to show anyone. What I got back was that every balance change after that was based on a number instead of my own opinion.

A dashboard that points, not one that dumps

It tells me which level is the problem rather than handing me raw event logs to interpret. What it costs: I had to decide up front what counts as a warning sign, which is a design decision in itself. That's the difference between a dashboard you open once and one you keep open while you work.

Build

  • The merge core, the level structure and the mobile UI
  • A live editor that changes move limits and goals without a rebuild
  • A dashboard surfacing win rates and the levels people get stuck on
  • Enough export to sanity-check a balancing decision outside the app when something looks odd

Result

  • 84.9% Win rate on level 3, flagged by the dashboard
  • Seconds From changing a move limit to seeing the result
  • 3 weeks Game, editor and dashboard, built together

Once I could see where people were breezing through, the editor did the rest: change the move limit, play it, check the number, move on. That's the whole thesis of the project and it held up. I'd never have caught an 84.9% win rate by feel, because level 3 felt fine to me. I built it.

You can't playtest your own game honestly: you already know every trick in it, which is exactly why the numbers matter.

Stack

  • Mobile web
  • Live level editor
  • Win-rate dashboard
  • Data export

Next: A/B testing two sets of move limits against each other, a proper drop-off funnel rather than win rates alone, and cloud save so I can test on one device and read the results on another.
