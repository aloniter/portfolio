Merge Lab

A merge puzzle where I built the tuning tools before I needed them: a level editor and a win-rate dashboard sitting right next to the game.

Role Solo Designer & Developer
Timeline 3 weeks
Platform Mobile Web
Focus Balancing workflow and instrumentation
Play Merge Lab

Outcome

The dashboard caught a level sitting at an 84.9% win rate, far too easy, and I hadn't noticed. Changed it in the editor, watched the number move, done in under a minute.

The Game and the Tools Beside It

Tuning by Feel Wasn't Working

Tuning a puzzle game solo usually goes: change a number, rebuild, play it yourself, decide it feels about right, move on. That's not tuning, that's guessing with extra steps, and you only find out you were wrong when someone else plays it. I wanted to know whether building the tools first would change how the game turned out.

Three Things That Had to Agree

Writing a merge loop is straightforward. Writing it while also building an editor that changes the game live and a dashboard that tells you something useful. That's three things that all have to agree with each other. The editor had to apply changes without a rebuild, or I'd never use it. And the dashboard had to point at the actual problem level, not hand me a wall of numbers I'd ignore by the second session.

What I Built

  • A merge puzzle built around filling orders, level by level
  • An editor inside the game: change move limits or goals and they apply immediately, no rebuild
  • A dashboard that calls out the hardest levels and where win rates fall off a cliff
  • Enough export to sanity-check a balancing decision outside the app when something looks odd

The Two Big Calls

Tools first, even though it felt backwards

I built the editor and the dashboard alongside the game instead of shipping the game and bolting tooling on later. What it costs: it took noticeably longer before I had anything that felt like a finished game to show anyone. What I got back was that every balance change after that was based on a number instead of my own opinion.

A dashboard that points, not one that dumps

It tells me which level is the problem, rather than handing me raw event logs to interpret. What it costs: I had to decide up front what actually counts as a warning sign, which is a real design decision in itself. But that's the difference between a dashboard you open once and one you keep open while you work.

Mine, All of It

  • Built the merge core, the level structure, and the mobile UI
  • Built the live editor that changes tuning without a rebuild
  • Built the dashboard that surfaces win rates and the levels people get stuck on
  • Treated the tooling the way a studio would, the kind of thing design, engineering, and QA all end up leaning on

What the Data Caught

84.9% Win rate on level 3, flagged by the dashboard
Seconds From changing a move limit to seeing the result

Once I could see where people were breezing through, the editor did the rest. Change the move limit, play it, check the number, move on. That's the whole thesis of the project, and it held up: I'd never have caught an 84.9% win rate by feel, because level 3 felt fine to me. I built it.

The Lesson That Stuck

  • You can't playtest your own game honestly: you already know every trick in it, which is exactly why the numbers matter
  • Next up: A/B testing two sets of move limits against each other
  • Next up: a proper drop-off funnel in the dashboard, not just win rates
  • Next up: cloud save, so I can test on one device and read the results on another
