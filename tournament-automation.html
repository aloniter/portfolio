Systems · LiveOps at SuperPlay

I kept seeing the same work. So I turned it into a system.

A recurring operational task was being done manually, again and again. It worked, but it was repetitive, easy to get wrong, and nobody had really questioned why it still needed to be manual.

Nobody assigned me to fix it. I just kept running into the same friction.

Role
Identified it, built it
Context
Live mobile game, LiveOps
Status
In production

This was internal work, so the implementation details, data and systems are intentionally not shown.

The call

The obvious solution was better documentation or a checklist. I didn't think that solved the real problem.

If people still have to repeat the same steps every time, the opportunity for mistakes is still there. So instead of documenting the process, I built a system that handled the repetitive part itself.

Building for the failure case

Automation alone wasn't enough. The more important part was deciding what should never be allowed to quietly go wrong, and building those checks directly into the workflow.

That meant making product decisions, not just technical ones:

  • What counts as an error?
  • What should stop the process?
  • What should still be allowed?

Too little validation and it doesn't protect anyone. Too much and the tool becomes harder to use than the problem it replaced.

Outcome

The repetitive work became part of a reliable internal workflow, with checks happening automatically instead of depending on someone remembering them.

The biggest win wasn't a few minutes saved. It was removing an entire class of avoidable mistakes.

What this says about how I work

I like finding the parts of a product or operation that everyone has learned to tolerate (repeated work, fragile workflows, manual checks) and asking whether they should exist at all. Then, when it makes sense, I build the thing that removes them.
