tournament setup — before / after

Problem

Getting a tournament live meant the same work every time: build the configuration, apply the segmentation, set the participation tiers, check it all by hand, then produce the recurring output that goes out alongside it. None of it was hard. All of it was repeated, and repeated configuration work is where mistakes come from — not from the difficult decisions, but from the twentieth time you type the same thing slightly differently.

Nobody assigned this. It was just the part of the week that kept costing time for no good reason.

Decisions

Generate the configuration, don't document it

The cheap fix is a checklist or a template — but a checklist still leaves a person typing the same values in, which is the part that goes wrong. So the system produces the configuration itself from a small set of inputs. What it costs — every variant has to be encoded up front. The segmentation options and participation tiers had to be pinned down as rules before anything could be generated, and that is slower than writing a document.

Validation inside the system, not after it

The checks run as part of generating the output rather than as a separate review pass, so a configuration can't quietly come out wrong and then get caught by whoever happens to be looking. What it costs — you have to decide in advance what counts as wrong, which is a real design decision rather than a technical one. Get the rules too loose and the validation is decoration; too strict and it blocks legitimate setups.

Build

  • Configuration generation from a small set of inputs, instead of manual setup
  • Segmentation logic covering multiple variants, so the common cases don't need hand-editing
  • Participation tiers handled as part of the configuration rather than bolted on afterwards
  • Validation rules that run on every generated configuration
  • Automated recurring output, produced on schedule rather than assembled each time

Result

  • ~10 min Of manual setup removed from every tournament
  • In production Running as part of the real LiveOps workflow

The ten minutes is the easy number to quote and the least interesting part. What actually changed is that the repeated configuration work is gone, so the failure mode it created is gone with it. The same output comes out the same way every time, and the checks happen whether or not anyone remembers to do them.

Stack

  • Configuration generation

  • Validation rules
  • Scheduled output
  • AI-assisted build
